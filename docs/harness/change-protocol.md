# 变更协议

本文件定义一次改动从理解到交付的最小闭环。代码规则见 [quality-rules.md](quality-rules.md)，验证矩阵见 [testing-guide.md](testing-guide.md)。

## 1. Impact Map

开始编辑前记录：

```md
- Goal: 要改变的行为，或要保持行为不变的重构目标
- Scope: 预计触达的 app、package、配置、文档和数据结构
- Risk: 权限/安全/迁移/备份/地图/AI/上传/发布/跨客户端影响
- No-touch: 用户已有改动、无关目录、密钥和生产数据
- Validation: 计划执行的测试、类型检查、构建和手工 QA
- Knowledge update: 是否需要更新架构、产品设计、Harness 或 README
```

## 2. 变更纪律

- 分支不使用 `codex/` 前缀；优先遵循维护者或 issue 已指定的名称。没有既定名称时使用 `<type>/<short-kebab-summary>`，例如 `docs/ui-design-harness`。
- 提交聚焦单一目的；业务行为变化、重构、依赖升级和格式化不要混在同一提交。
- 不覆盖 `.env*`、本地数据库、上传文件或未跟踪目录。
- 修改共享包时，列出所有直接消费端并验证受影响的 Web、Server 或 Mobile。
- 修改 API 时，说明请求、成功响应、失败响应、权限和兼容性。
- 修改数据库 schema 时，迁移必须纳入版本控制，并说明回滚/向前修复策略。
- 修改地图能力时，检查配置代理、权限、坐标数据、投影、统计口径和响应式布局。
- 修改入口、领域边界、测试策略或运行方式时，同步更新相应文档。

## 3. 风险分级

| 等级 | 典型变更 | 最低要求 |
| --- | --- | --- |
| 低 | 文案、文档、局部样式、纯函数 | 触达范围检查、差异检查 |
| 中 | 页面交互、API 编排、共享包、图片处理 | 类型检查、相关测试、构建、关键手工 QA |
| 高 | 认证授权、密钥、迁移、备份导入、生产部署、发布 | 中风险全部要求，加失败路径、安全检查、回滚或恢复说明 |

## 4. 实施与验证

1. 先运行最接近改动的现有测试，建立基线。
2. 小步修改；每一步保持可解释、可回滚。
3. 先执行专项测试，再执行受影响 workspace 的类型检查和构建。
4. UI 变更同时验证桌面与移动断点；涉及地图时使用脱敏数据。
5. 对没有自动化覆盖的行为记录手工步骤和观察结果。

## 5. 交付说明

提交或 PR 至少包含：

- 改了什么，以及为什么。
- 影响的 app/package、接口、数据和用户角色。
- 已执行验证及结果。
- 未执行项及原因。
- 已知风险、回滚/恢复方式和后续任务。
- 同步更新的设计、架构或 Harness 文档。
